# 1. Statistics: Unused Objects
Concepto: Identificación de recolecciones de estadísticas en tablas que no han tenido acceso de lectura (Select), inserción, actualización o borrado en un periodo determinado.
El Problema: Desperdicio masivo de recursos de CPU y entrada/salida (I/O) durante la ventana de mantenimiento. Recolectar estadísticas en objetos "muertos" alarga los procesos de carga sin aportar valor al optimizador.
Lógica de validación: Cruzar DBC.StatsV con DBC.ObjectUsage o las tablas de log de DBQL (ObjectColumnHierarchy). Si LastAlterTimeStamp o el uso de objetos es nulo o muy antiguo, la estadística es candidata a ser eliminada.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Unused_Tables AS (
SELECT 
    s.DatabaseName, 
    s.TableName,
    CAST(SUM(t.CurrentPerm) / (1024.0**3) AS DECIMAL(18,2)) AS Size_GB,
    MAX(CAST(s.LastCollectTimeStamp AS DATE)) AS Last_Stat_Collect,
    -- Si ObjectUsage está habilitado, usamos LastAccessTimeStamp
    MAX(u.LastAccessTimeStamp) AS Last_Actual_Access
FROM DBC.StatsV s
INNER JOIN (
    SELECT DatabaseName, TableName, TableKind, SUM(CurrentPerm) AS CurrentPerm
    FROM DBC.TableSizeV
    GROUP BY 1, 2, 3
) t ON s.DatabaseName = t.DatabaseName AND s.TableName = t.TableName
LEFT JOIN DBC.ObjectUsage u 
    ON s.DatabaseName = u.DatabaseName 
    AND s.TableName = u.TableName
WHERE t.TableKind = 'T'
  AND CAST(s.LastCollectTimeStamp AS DATE) >= CURRENT_DATE - 30 -- Stats movidas recientemente
GROUP BY 1, 2
HAVING (Last_Actual_Access < CURRENT_DATE - 30 OR Last_Actual_Access IS NULL)
   AND Last_Stat_Collect > Last_Actual_Access -- Se colectó después del último uso
ORDER BY Size_GB DESC;
)
SELECT 
    'Statistics Management', 
    1, 
    'Unused Objects',
    COUNT(DISTINCT ut.TableName),
    COALESCE(SUM(l.AMPCPUTime + l.ParserCPUTime), 0), -- Sumamos el CPU de los comandos de recolección
    'Tables with stats collection consuming CPU but no usage'
FROM Unused_Tables ut
LEFT JOIN PDCRINFO.DBQLogTbl_Hst l
    ON ut.DatabaseName = l.DefaultDatabase -- O cruzar extrayendo la base de datos del QueryText si aplica
    AND l.StatementType = 'Collect Statistics'
    AND l.LogDate = CURRENT_DATE - 1
    AND l.QueryText LIKE '%' || ut.TableName || '%';


2. Statistics: Sample Candidates
Concepto: Determinación de columnas candidatas para usar USING SAMPLE en lugar de un FULL SCAN. Teradata recomienda muestreo cuando la columna tiene una alta cardinalidad y una distribución uniforme.
El Problema: El costo de recolectar estadísticas al 100% en tablas multiterabyte es prohibitivo. Si el optimizador puede obtener una confianza del 95-99% con un sample del 2% al 10%, el ahorro de CPU es exponencial.
Lógica de validación: Analizar DBC.StatsV. Si UniqueValueCount es muy cercano a RowCount (alta unicidad) y el tamaño de la tabla supera un umbral (ej. > 100GB), marcar como candidato a Sample.

SELECT 
    S.DatabaseName, 
    S.TableName, 
    S.ColumnName,
    CAST(SUM(T.CurrentPerm) / (1024.0**3) AS DECIMAL(18,2)) AS Size_GB,
    S.RowCount,
    S.UniqueValueCount,
    CAST(CAST(S.UniqueValueCount AS DECIMAL(18,4)) / NULLIF(S.RowCount, 0) AS DECIMAL(18,4)) AS Uniqueness_Ratio,
    S.LastCollectTimeStamp
FROM DBC.StatsV S
INNER JOIN (
    -- Agregamos el tamaño por tabla para evitar duplicados en el join
    SELECT DatabaseName, TableName, SUM(CurrentPerm) AS CurrentPerm
    FROM DBC.TableSizeV
    GROUP BY 1, 2
) T 
    ON S.DatabaseName = T.DatabaseName 
    AND S.TableName = T.TableName
WHERE S.RowCount > 100000000  -- Solo tablas con más de 100M de filas
  AND (T.CurrentPerm / (1024.0**3)) > 50 -- Solo tablas que pesen más de 50GB
  AND Uniqueness_Ratio >= 0.95
  AND S.ColumnName <> '*' -- Enfocarnos en columnas individuales, no en la tabla completa
  AND S.SampleSizePct IN (0, 100) -- Solo las que actualmente se colectan al 100%
GROUP BY 1, 2, 3, 5, 6, 7, 8
ORDER BY Size_GB DESC;
	
	
3. Statistics: Missing at PARTITION level
Concepto: Las tablas con Partition Primary Index (PPI) requieren estadísticas específicas sobre la columna virtual PARTITION para que el optimizador realice un "Partition Elimination" eficiente.
El Problema: Sin estadísticas de partición, el optimizador no sabe cuántas filas hay en cada segmento, lo que puede resultar en un "Full Table Scan" en lugar de acceder solo a las particiones necesarias.
Lógica de validación: Consultar DBC.TablesV para identificar tablas con PartitioningLevel > 0 y verificar en DBC.StatsV que no exista una entrada donde ColumnName sea 'PARTITION'.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Table_CPU_Yesterday AS (
    SELECT o.ObjectDatabaseName, o.ObjectTableName, SUM(l.AMPCPUTime + l.ParserCPUTime) as TotalCPU
    FROM PDCRINFO.DBQLObjTbl_Hst o
    INNER JOIN PDCRINFO.DBQLogTbl_Hst l ON o.QueryID = l.QueryID AND o.LogDate = l.LogDate
    WHERE o.LogDate = CURRENT_DATE - 1 AND l.LogDate = CURRENT_DATE - 1
    GROUP BY 1, 2
),
Missing_Partition AS (
    SELECT DISTINCT ic.DatabaseName, ic.TableName
    FROM DBC.IndexConstraints ic
    INNER JOIN DBC.TablesV t ON ic.DatabaseName = t.DatabaseName AND ic.TableName = t.TableName
    LEFT JOIN DBC.StatsV s ON ic.DatabaseName = s.DatabaseName AND ic.TableName = s.TableName AND s.ColumnName = 'PARTITION'
    WHERE ic.ConstraintType = 'Q' AND s.ColumnName IS NULL
)
SELECT 'Statistics Management', 3, 'Missing PARTITION Stats', COUNT(DISTINCT mp.TableName), COALESCE(SUM(tc.TotalCPU), 0), 'PPI tables without PARTITION stats and their impact CPU'
FROM Missing_Partition mp LEFT JOIN Table_CPU_Yesterday tc ON mp.DatabaseName = tc.ObjectDatabaseName AND mp.TableName = tc.ObjectTableName;


4. Statistics: Missing at Table Level
Concepto: Tablas que están siendo consultadas activamente pero no tienen ninguna estadística recolectada (ni siquiera un COLLECT STATISTICS ON TableName).
El Problema: El optimizador debe confiar en "Dynamic Amps Sampling" (un vistazo rápido a pocos cilindros), lo cual es poco fiable para tablas grandes o con skew (sesgo), resultando en estimaciones de cardinalidad erróneas y planes de ejecución subóptimos.
Lógica de validación: Identificar tablas en DBC.TablesV que aparecen en DBC.DBQLogTbl (actividad reciente) pero que no tienen registros correspondientes en DBC.StatsV.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Table_CPU_Yesterday AS ( /* ... Mismo bloque CTE Table_CPU_Yesterday ... */ 
    SELECT o.ObjectDatabaseName, o.ObjectTableName, SUM(l.AMPCPUTime + l.ParserCPUTime) as TotalCPU
    FROM PDCRINFO.DBQLObjTbl_Hst o INNER JOIN PDCRINFO.DBQLogTbl_Hst l ON o.QueryID = l.QueryID AND o.LogDate = l.LogDate
    WHERE o.LogDate = CURRENT_DATE - 1 AND l.LogDate = CURRENT_DATE - 1 GROUP BY 1, 2
),
Missing_Table_Stats AS (
    SELECT DISTINCT o.ObjectDatabaseName AS DatabaseName, o.ObjectTableName AS TableName
    FROM PDCRINFO.DBQLObjTbl_Hst o
    INNER JOIN DBC.TablesV t ON o.ObjectDatabaseName = t.DatabaseName AND o.ObjectTableName = t.TableName
    LEFT JOIN DBC.StatsV s ON o.ObjectDatabaseName = s.DatabaseName AND o.ObjectTableName = s.TableName
    WHERE o.LogDate = CURRENT_DATE - 1 AND t.TableKind = 'T' AND o.ObjectType = 'Tab' AND s.TableName IS NULL
)
SELECT 'Statistics Management', 4, 'Missing Stats Table-Level', COUNT(DISTINCT mt.TableName), COALESCE(SUM(tc.TotalCPU), 0), 'Tables used yesterday but without any stats'
FROM Missing_Table_Stats mt LEFT JOIN Table_CPU_Yesterday tc ON mt.DatabaseName = tc.ObjectDatabaseName AND mt.TableName = tc.ObjectTableName;


5. Statistics: Missing at Index Level
Concepto: Falta de estadísticas en índices secundarios (SI), índices de join (JI) o columnas que forman parte del Primary Index (PI).
El Problema: Teradata utiliza los índices para mejorar el acceso, pero si no conoce su demografía, puede decidir no usarlos o, peor aún, elegir un índice que no es selectivo, degradando el rendimiento.
Lógica de validación: Comparar DBC.IndicesV contra DBC.StatsV. Cualquier índice definido que no tenga una entrada de estadística correspondiente se considera una "Best Practice Violation".

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Table_CPU_Yesterday AS ( /* ... Mismo bloque CTE ... */ 
    SELECT o.ObjectDatabaseName, o.ObjectTableName, SUM(l.AMPCPUTime + l.ParserCPUTime) as TotalCPU
    FROM PDCRINFO.DBQLObjTbl_Hst o INNER JOIN PDCRINFO.DBQLogTbl_Hst l ON o.QueryID = l.QueryID AND o.LogDate = l.LogDate
    WHERE o.LogDate = CURRENT_DATE - 1 AND l.LogDate = CURRENT_DATE - 1 GROUP BY 1, 2
),
Missing_Index_Stats AS (
    SELECT i.DatabaseName, i.TableName
    FROM DBC.IndicesV i
    LEFT JOIN DBC.StatsV s ON i.DatabaseName = s.DatabaseName AND i.TableName = s.TableName AND i.ColumnName = s.ColumnName
    WHERE i.IndexType IN ('P', 'S', 'Q', 'J') AND s.ColumnName IS NULL
	group by 1,2
)
SELECT 'Statistics Management', 5, 'Missing Stats Index-Level', COUNT(DISTINCT mi.TableName), COALESCE(SUM(tc.TotalCPU), 0), 'Missing stats on indexes (PI, SI, JI, PPI)'
FROM Missing_Index_Stats mi LEFT JOIN Table_CPU_Yesterday tc ON mi.DatabaseName = tc.ObjectDatabaseName AND mi.TableName = tc.ObjectTableName;


6. Statistics: Stale
Concepto: Estadísticas cuya fecha de última recolección (LastCollectTimeStamp) es excesivamente antigua en comparación con la tasa de cambio de la tabla.
El Problema: Las estadísticas "viejas" no reflejan la realidad de los datos actuales. El optimizador tomará decisiones basadas en una fotografía del pasado, lo que es crítico en tablas con crecimiento volátil.
Lógica de validación: Filtrar DBC.StatsV donde LastCollectTimeStamp < CURRENT_DATE - 30 (o el umbral de política de la empresa).

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Table_CPU_Yesterday AS ( /* ... Mismo bloque CTE ... */ 
    SELECT o.ObjectDatabaseName, o.ObjectTableName, SUM(l.AMPCPUTime + l.ParserCPUTime) as TotalCPU
    FROM PDCRINFO.DBQLObjTbl_Hst o INNER JOIN PDCRINFO.DBQLogTbl_Hst l ON o.QueryID = l.QueryID AND o.LogDate = l.LogDate
    WHERE o.LogDate = CURRENT_DATE - 1 AND l.LogDate = CURRENT_DATE - 1 GROUP BY 1, 2
),
Stale_Stats AS (
    SELECT  DatabaseName, TableName
    FROM DBC.StatsV
    WHERE CAST(LastCollectTimeStamp AS DATE) < CURRENT_DATE - 30 AND DatabaseName NOT IN ('DBC', 'Crashdumps', 'Sys_Calendar')
	group by DatabaseName, TableName
)
SELECT 'Statistics Management', 6, 'Stale Statistics', COUNT(DISTINCT sst.TableName), COALESCE(SUM(tc.TotalCPU), 0), 'Tables with stats older than 30 days and their impact CPU'
FROM Stale_Stats sst
LEFT JOIN Table_CPU_Yesterday tc
ON sst.DatabaseName = tc.ObjectDatabaseName AND sst.TableName = tc.ObjectTableName;


7. Statistics: Zero
Concepto: Estadísticas que reflejan un RowCount = 0 a pesar de que la tabla contiene datos actualmente.
El Problema: Es uno de los problemas más peligrosos. Si el optimizador cree que la tabla está vacía, suele elegir planes de "Product Join", lo que puede colgar el sistema si la tabla en realidad tiene millones de filas.
Lógica de validación: Buscar en DBC.StatsV registros con RowCount = 0 y verificar el conteo actual o el tamaño físico en DBC.TableSize.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Table_CPU_Yesterday AS ( /* ... Mismo bloque CTE ... */ 
    SELECT o.ObjectDatabaseName, o.ObjectTableName, SUM(l.AMPCPUTime + l.ParserCPUTime) as TotalCPU
    FROM PDCRINFO.DBQLObjTbl_Hst o INNER JOIN PDCRINFO.DBQLogTbl_Hst l ON o.QueryID = l.QueryID AND o.LogDate = l.LogDate
    WHERE o.LogDate = CURRENT_DATE - 1 AND l.LogDate = CURRENT_DATE - 1 GROUP BY 1, 2
),
Zero_Stats AS (
    SELECT s.DatabaseName, s.TableName
    FROM DBC.StatsV s INNER JOIN DBC.TableSizeV ts ON s.DatabaseName = ts.DatabaseName AND s.TableName = ts.TableName
    WHERE s.RowCount = 0 GROUP BY 1, 2 HAVING SUM(ts.CurrentPerm) > 0
)
SELECT 'Statistics Management', 7, 'Zero Count Statistics', COUNT(DISTINCT zs.TableName), COALESCE(SUM(tc.TotalCPU), 0), 'Stats records with Zero Count values on populated tables'
FROM Zero_Stats zs LEFT JOIN Table_CPU_Yesterday tc ON zs.DatabaseName = tc.ObjectDatabaseName AND zs.TableName = tc.ObjectTableName;


8. Statistics: Multicolumn
Concepto: Gestión de estadísticas sobre múltiples columnas combinadas para capturar correlaciones entre ellas (ej. Ciudad y Código Postal).
El Problema: Existe un límite físico para almacenar los valores de los histogramas. Si la longitud combinada de las columnas excede el MaxValueLength definido, la estadística se trunca, perdiendo precisión en la estimación de selectividad.
Lógica de validación: Revisar en DBC.StatsV las estadísticas multicolumna donde la suma de las longitudes de los tipos de datos asociados sea mayor al valor configurado en el sistema para almacenamiento de histogramas.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Table_CPU_Yesterday AS ( /* ... Mismo bloque CTE ... */ 
    SELECT o.ObjectDatabaseName, o.ObjectTableName, SUM(l.AMPCPUTime + l.ParserCPUTime) as TotalCPU
    FROM PDCRINFO.DBQLObjTbl_Hst o INNER JOIN PDCRINFO.DBQLogTbl_Hst l ON o.QueryID = l.QueryID AND o.LogDate = l.LogDate
    WHERE o.LogDate = CURRENT_DATE - 1 AND l.LogDate = CURRENT_DATE - 1 GROUP BY 1, 2
),
Multicolumn_Stats AS (
    SELECT DISTINCT DatabaseName, TableName
    FROM DBC.StatsV 
    WHERE ExpressionCount > 1  -- Identifica stats combinadas
      AND MaxValueLength < 25
)
SELECT 'Statistics Management', 8, 'Multicolumn MaxValueLength', COUNT(DISTINCT ms.TableName), COALESCE(SUM(tc.TotalCPU), 0), 'Multicolumn combined length exceeding defined maxvaluelength'
FROM Multicolumn_Stats ms LEFT JOIN Table_CPU_Yesterday tc ON ms.DatabaseName = tc.ObjectDatabaseName AND ms.TableName = tc.ObjectTableName;


9. Statistics: Skipped and Sample
Concepto: Monitoreo de estadísticas que el sistema decidió no actualizar (Skipped) porque el cambio en los datos no era significativo, o que están usando un muestreo (Sample).
El Problema: Si una estadística se marca como "Skipped" sistemáticamente pero hay errores de plan, el umbral de "Threshold" de Teradata podría estar mal configurado. El exceso de "Sample" puede ser impreciso para datos muy sesgados.
Lógica de validación: Analizar la columna UsageType y los flags de System Determined Threshold en DBC.StatsV.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Table_CPU_Yesterday AS ( /* ... Mismo bloque CTE ... */ 
    SELECT o.ObjectDatabaseName, o.ObjectTableName, SUM(l.AMPCPUTime + l.ParserCPUTime) as TotalCPU
    FROM PDCRINFO.DBQLObjTbl_Hst o INNER JOIN PDCRINFO.DBQLogTbl_Hst l ON o.QueryID = l.QueryID AND o.LogDate = l.LogDate
    WHERE o.LogDate = CURRENT_DATE - 1 AND l.LogDate = CURRENT_DATE - 1 GROUP BY 1, 2
),
Sampled_Stats AS (
    SELECT DISTINCT DatabaseName, TableName
    FROM DBC.StatsV 
    WHERE (SampleSizePct > 0 AND SampleSizePct < 100) 
       OR StatsSkipCount > 0
)
SELECT 'Statistics Management', 9, 'Skipped and Sample Stats', COUNT(DISTINCT sst.TableName), COALESCE(SUM(tc.TotalCPU), 0), 'Statistics records being skipped or using sample stats'
FROM Sampled_Stats sst LEFT JOIN Table_CPU_Yesterday tc ON sst.DatabaseName = tc.ObjectDatabaseName AND sst.TableName = tc.ObjectTableName;


10. Statistics: DBC Recommendations
Concepto: Recolección de estadísticas sobre las tablas internas del sistema (DBC) y del repositorio de rendimiento (PDCR).
El Problema: El motor de Teradata también usa el optimizador para consultar sus propias tablas de metadatos. Si DBC.TVM, DBC.Obj o PDCRDATA no tienen stats, las consultas de monitoreo y el propio Parsing de los usuarios se vuelven lentos.
Lógica de validación: Verificar la existencia de estadísticas en las bases de datos DBC y PDCRDATA comparándolas con los scripts de mejores prácticas de Teradata (generalmente provistos en la documentación de Database Administration).

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Table_CPU_Yesterday AS ( /* ... Mismo bloque CTE ... */ 
    SELECT o.ObjectDatabaseName, o.ObjectTableName, SUM(l.AMPCPUTime + l.ParserCPUTime) as TotalCPU
    FROM PDCRINFO.DBQLObjTbl_Hst o INNER JOIN PDCRINFO.DBQLogTbl_Hst l ON o.QueryID = l.QueryID AND o.LogDate = l.LogDate
    WHERE o.LogDate = CURRENT_DATE - 1 AND l.LogDate = CURRENT_DATE - 1 GROUP BY 1, 2
),
Missing_DBC_Stats AS (
    SELECT DISTINCT t.DatabaseName, t.TableName
    FROM DBC.TablesV t
    LEFT JOIN DBC.StatsV s ON t.DatabaseName = s.DatabaseName AND t.TableName = s.TableName
    WHERE t.DatabaseName IN ('DBC', 'PDCRDATA') AND t.TableKind = 'T' AND s.TableName IS NULL
)
SELECT 'Statistics Management', 10, 'Missing DBC/PDCR Stats', COUNT(DISTINCT md.TableName), COALESCE(SUM(tc.TotalCPU), 0), 'Missing recommended stats in DBC and PDCRDATA tables'
FROM Missing_DBC_Stats md LEFT JOIN Table_CPU_Yesterday tc ON md.DatabaseName = tc.ObjectDatabaseName AND md.TableName = tc.ObjectTableName;


11. Statistics: Redundant / Overlapping Stats
Concepto: Presencia de estadísticas en una columna individual (Col A) que ya es la columna líder de una estadística multicolumna (Col A, Col B).
El Problema: Desperdicio doble de CPU y espacio en el diccionario de datos. El optimizador de Teradata puede derivar la información de la columna líder desde el histograma multicolumna sin necesidad de la estadística individual.
Lógica de validación: Buscar en DBC.StatsV estadísticas de una sola columna cuyo ColumnName coincida con el primer elemento en el campo StatsResults de una estadística compuesta para la misma tabla.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Redundant_Stats AS (
  SELECT a.DatabaseName, a.TableName
  FROM DBC.StatsV a
  INNER JOIN DBC.StatsV b ON a.DatabaseName = b.DatabaseName AND a.TableName = b.TableName
  WHERE a.ExpressionCount = 1 AND b.ExpressionCount > 1 AND b.ColumnName LIKE a.ColumnName || ',%'
)
SELECT 'Statistics Management', 11, 'Redundant', COUNT(DISTINCT TableName), 0, 'Single column stats that overlap with leading columns of multi-column stats'
FROM Redundant_Stats;


12. Statistics: Extrapolation (Growth Variance)
Concepto: El proceso mediante el cual Teradata ajusta las estadísticas existentes basándose en el conteo de filas actual cuando la recolección está desactualizada.
El Problema: La extrapolación es lineal; si la distribución de los nuevos datos no es igual a la anterior (ej. nuevos rangos de fechas), el optimizador generará planes erróneos por subestimación masiva.
Lógica de validación: Comparar el RowCount de la última recolección en DBC.StatsV contra el CurRowCount derivado de DBC.TableSize (basado en el promedio de bytes por fila). Si la varianza supera el 10-20%, se requiere recolección urgente.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Extrapolation_Risk AS (
  SELECT s.DatabaseName, s.TableName
  FROM DBC.StatsV s
  INNER JOIN DBC.TableSizeV ts ON s.DatabaseName = ts.DatabaseName AND s.TableName = ts.TableName
  WHERE s.RowCount < 1000 
  GROUP BY 1, 2
  HAVING SUM(ts.CurrentPerm) > 1073741824 -- Tablas de mas de 1GB que creen tener menos de 1000 filas
)
SELECT 'Statistics Management', 12, 'Extrapolation Risk', COUNT(DISTINCT TableName), 0, 'Massive discrepancy between Stats RowCount and Physical Size'
FROM Extrapolation_Risk;


13. Statistics: Analyze Feature (Auto-Stats Readiness)
Concepto: Evaluación de la compatibilidad de las estadísticas actuales con las funciones de Automated Statistics Management de Teradata.
El Problema: Las estadísticas creadas con sintaxis antigua o parámetros manuales rígidos (como un SAMPLE fijo muy pequeño) bloquean la capacidad del motor de decidir dinámicamente cuándo y cómo recolectar (Auto-Sample).
Lógica de validación: Identificar en DBC.StatsV registros donde el campo de opciones de recolección (ExpressionText) contenga valores "hardcoded" de SAMPLE o MAXINTERVALS.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Hardcoded_Sample AS (
  SELECT DISTINCT DatabaseName, TableName
  FROM DBC.StatsV
  WHERE SampleSizePct > 0 AND SampleSizePct < 100 
)
SELECT 'Statistics Management', 13, 'Hardcoded Samples', COUNT(DISTINCT TableName), 0, 'Stats with forced USING SAMPLE overriding System Auto-Stats intelligence'
FROM Hardcoded_Sample;


14. Statistics: Missing on Join Columns (Non-Indexed)
Concepto: Columnas que se utilizan frecuentemente en cláusulas ON de JOINs pero que no tienen índices ni estadísticas.
El Problema: Teradata debe decidir entre redistribuir los datos o duplicarlos en spool. Sin estadísticas en estas columnas de unión, el riesgo de elegir un "Product Join" o causar un "Skewed Redistribution" es altísimo.
Lógica de validación: Minar la tabla DBC.DBQLStepTbl buscando columnas en los pasos de "Join" que no tengan una entrada en DBC.StatsV.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Missing_Keys AS (
  SELECT c.DatabaseName, c.TableName
  FROM DBC.ColumnsV c
  LEFT JOIN DBC.StatsV s ON c.DatabaseName = s.DatabaseName AND c.TableName = s.TableName AND c.ColumnName = s.ColumnName
  WHERE c.ColumnName LIKE ANY ('%_ID', '%_KEY', '%_CD', '%_CODE') AND s.ColumnName IS NULL AND c.DatabaseName NOT IN ('DBC', 'Crashdumps', 'Sys_Calendar')
)
SELECT 'Statistics Management', 14, 'Missing Key Columns', COUNT(DISTINCT TableName), 0, 'Heuristic: ID/KEY/CODE columns likely used in JOINs without statistics'
FROM Missing_Keys;

15. Statistics: Excessive Histogram Size (Dictionary Bloat)
Concepto: Acumulación excesiva de estadísticas individuales en una sola tabla, lo que genera histogramas masivos en el Diccionario de Datos.
El Problema: Cada vez que se hace un Explain de una consulta, el optimizador debe cargar los histogramas en memoria. Demasiadas estadísticas ralentizan el tiempo de "Parsing" y pueden causar que la base de datos DBC se quede sin espacio (Spool o Permanente).
Lógica de validación: Realizar un conteo de entradas en DBC.StatsV agrupado por DatabaseName y TableName. Alertar sobre tablas que superen las 50 recolecciones individuales.

INSERT INTO sysdba.Stats_Assessment_Metrics (Section_Name, Metric_ID, Metric_Name, Object_Count, CPU_Seconds, Finding_Desc)
WITH Bloated_Dict AS (
  SELECT DatabaseName, TableName
  FROM DBC.StatsV
  GROUP BY 1, 2
  HAVING COUNT(*) > 50
)
SELECT 'Statistics Management', 15, 'Excessive Histograms', COUNT(DISTINCT TableName), 0, 'Tables with more than 50 distinct statistics collections bloating DBC'
FROM Bloated_Dict;
